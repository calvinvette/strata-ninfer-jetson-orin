# Open-response adaptive recovery: selector arm

This is a same-day correctness pair on Orin, using the pinned Coder IQ1_M model and current capture binary. It is a diagnostic follow-up to the short-response retrieval probe. The held-out prompt is the existing 7,501-token archive with its final exact-answer instruction replaced by a request for a detailed report; the source workload has 7,512 tokens, and the long arm uses its 2,048-token suffix. The sequence is short–long–short, with 128 generated tokens requested per request, seed `2026102251`, prompt cache 6, and the layer-31/expert-22 reciprocal-SiLU selector enabled. Model, shards, source, and binary identities are recorded in `campaign.json`.

Both adaptive and delayed-control arms passed their run supervisors. The adaptive run took 616.64 s and reached 14.17 GiB minimum host/admission availability; delayed took 623.79 s and reached 14.27 GiB. The workload generated 128 tokens for each of its three requests in both arms. No cgroup memory events were recorded. These timings are incidental to a correctness capture; clocks varied during the runs and this is not a performance comparison.

On the final short recovery request, adaptive output differed from the initial short request at 113/128 token IDs; the first differing ID was at index 0. Delayed control matched all 128. The first differing accepted-prefix GDN hash in the adaptive trace was ordinal 17; delayed GDN hashes remained exact. At model layer 21, position 515, routes and router weights matched. The rank-9 expert-132 row changed in all 2,560 values (relative L2 `0.016716`), and the combined MoE output changed in 2,559/2,560 values (relative L2 `0.001528`). The all-layer verifier-input capture first differs at model layer 22 (relative L2 `0.0009572`); the layer-20 residual-boundary fields are exact. Delayed layer-21 rows and combined MoE output are bit-identical.

The matched no-selector pair is recorded in the sibling [`layer21-position515-open-response-direct-division-128pos`](../layer21-position515-open-response-direct-division-128pos/README.md) report. Across selector configurations, all three request token sequences are identical, all 387 accepted-prefix GDN hash records are identical, and the layer-21 route, parts, and combined-output capture files are byte-identical. In both adaptive arms, expert 132 moves CPU→GPU at layer 21/position 515; its row and the combined MoE output change identically. Both adaptive recoveries differ from the initial short output on 113/128 tokens, first GDN hash difference ordinal 17; both delayed controls are exact. The trace admits expert 132 at position 2138/round 220 (`132 → 87`) in both arms. Thus this open prompt shows adaptive drift and owner migration, but no measurable selector-specific effect. It does not reproduce the earlier position-598/round-88 decision. Neither selector is a recovery correction or a default change.

An independent same-input [`native_expert_parity` oracle](../operator-oracle-open-response/layer21-expert132/README.md) confirms the row change: the initial CPU service row and recovery GPU row each match their owner-specific oracle bitwise, while CPU and GPU oracle rows differ in all 2,560 values (relative L2 `0.016716`). The oracle input is identical across both requests and both selector configurations.
