# Open-response adaptive recovery: no-selector control

This is the same-day direct-division/no-selector control for the [open-response selector pair](../layer21-position515-expert22-open-response-128pos/README.md). It uses the pinned Coder IQ1_M model, same binary and seed `2026102251`, the same 7,512-token held-out report prompt (2,048-token suffix), short–long–short sequence, 128-token request caps, and layer-21 position-515 capture. The only configuration difference is that the layer-31/expert-22 reciprocal-SiLU selector is absent. Identities and source hashes are in `campaign.json`.

Both arms passed. Adaptive took 616.36 s with 14.09 GiB minimum host/admission availability; delayed control took 654.36 s with 14.27 GiB. Each produced 128 tokens for all three requests. Cgroup memory events were zero. These are correctness-capture timings, not a serving-performance comparison; clocks were dynamic and energy was not measured.

Adaptive recovery differed from its initial short response at 113/128 token IDs, with first GDN hash difference at ordinal 17. Delayed recovery matched all 128 tokens and state hashes. At layer 21/position 515, routes and router weights match between initial and recovery. Expert 132 (rank 9) moves CPU→GPU; its output row changes in all 2,560 values (relative L2 `0.016716`) and the combined MoE output changes in 2,559/2,560 values (relative L2 `0.001528`). The first changed verifier input is layer 22 (relative L2 `0.0009572`); the layer-20 boundary is exact. Delayed layer-21 rows and combined output are bit-identical.

Comparison with the selector arm finds exact equality across the three request token sequences, all 387 accepted-prefix GDN hash records, and layer-21 route, parts, and combined-output capture files. Both adaptive traces admit expert 132 at position 2138/round 220 (`132 → 87`). The open prompt therefore reproduces adaptive drift and the CPU→GPU migration without the selector; it shows no selector-specific effect and does not reproduce the earlier position-598/round-88 choice. This does not invalidate the earlier selector-associated result for its different prompt/sequence, but limits that finding to that workload. Neither selector is a recovery correction or a default change.

The [`native_expert_parity` same-input oracle](../operator-oracle-open-response/layer21-expert132/README.md) confirms the row transition: initial CPU and recovery GPU service rows match their independent owner-specific oracle bitwise, and the oracle rows differ in all 2,560 values (relative L2 `0.016716`). The activation is identical between requests and selector configurations.

Raw captures and machine-readable analyses are in this directory and its selector sibling. Model files and build products remain outside Git.
