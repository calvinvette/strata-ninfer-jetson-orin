# Held-out short-chain recovery at 256 generated tokens

This extends the held-out open-response recovery probe to 256 output tokens per request. It uses the same pinned Coder IQ1_M model and binary as the 128-token pair, seed `2026102251`, the same held-out report workload, and the short–short–short sequence. The layer-31/expert-22 selector is disabled. The adaptive cap-8 arm is paired with delayed control; each arm makes 256 tokens for the initial, intermediate and recovery requests. Artifact identities and the workload hash are in `campaign.json`.

Both arms passed. Adaptive recovery differs from the initial short response at 237/256 token IDs, first at output index 10. Its aggregate persistent fingerprints differ at every recovery prefix, and per-GDN accepted-prefix hashes first differ at ordinal 17. Delayed control matches all 256 token IDs and all state/GDN fingerprints. This extends the observed adaptive drift beyond the 128-token limit; it does not provide a numerical bound or meet the Phase 5 drift contract.

The 256-token all-layer capture was not enabled, so this run does not identify a new operator seam or directly compare raw recurrent/conv values. The preceding 128-token open-response capture and its same-input oracle localize one owner-dependent boundary; this longer run tests persistence of the mismatch over an extended chain only.

Adaptive and delayed runs took 768.06 s and 791.21 s. Their minimum physical host/admission availability was 14.14 and 14.19 GiB, respectively. Across 735/758 supervisor samples, cgroup low/high/max/OOM/OOM-kill event counts stayed zero. Clocks varied naturally; EMC frequency was unavailable, and energy was not measured. These are correctness-run durations, not a performance comparison.

`selected-position-analysis.json` contains the token/state/GDN comparisons; `long-chain-summary.json` is regenerated by `summarize_long_chain.py`. Raw service logs and state-hash traces remain alongside each arm. No model or build product is stored here.
