# Phase 3 full 2048-token owned prefill chunk

This supervised Orin request exercised an exact 2048-token formatted prompt against an owned 2048-token prefill chunk. It follows the earlier admission screen whose 172-token prompt did not reach the configured chunk size.

The input was generated by `tools/integration/prepare_controls.py` using the pinned model tokenizer and chat template, then retained as one workload in `workloads.json`. The server used the Qwen3.8-Flash-Next Coder IQ1_M validation model and MTP runtime pack in `~/models/strata-orin-validation`; CUDA 12; automatic expert cache; context 4096; FP16 KV; speculation 4; prefill chunk 2048; `--no-prefill-borrow`; `--vram-reserve-mib 3072`; and PCIe fraction 0.55. One warmup and one measured streamed API request each reported exactly 2048 prompt tokens and 8 generated tokens. The measured request completed. This is workload completion, not numerical or long-context quality qualification.

`run_control.py` enforced a 6,442,450,944-byte six-GiB minimum `MemAvailable` floor. Minimum availability was 8,610,402,304 bytes (8.02 GiB). The existing reservation trace reports a 1520 MiB prefill-workspace hold, 219 MiB MTP-bind hold and 3072 MiB VRAM-slack hold. They are separate from requested allocation observations. Clocks were unchanged; energy was not measured.

This confirms one full configured chunk completes with the short eight-token output cap. It does not test a late allocation failure, longer-context quality, cancellation cleanup, sustained behavior or performance. The single measured request is not a timing comparison.

`matrix.json`, cell configuration, capabilities, full request record, owner summary and supervisor memory/tegrastats logs are preserved. `SHA256SUMS` covers the artifacts. Model files remain in `~/models` and are not included.
