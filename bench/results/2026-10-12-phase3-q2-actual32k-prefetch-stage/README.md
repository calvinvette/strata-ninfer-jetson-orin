# Q2_0 32K prompt: prefetch fill versus host staging — Orin — 2026-10-12

This Phase 3 transfer screen compares two real-request modes with the same Q2_0 model, 32,768-token prompt, 8-token output, and 3,000 expert-cache slots. Both use asynchronous prefetch (`STRATA_IO_PREFETCH=1`, eight workers); the candidate arm additionally stages prefetched data into host buffers (`STRATA_IO_PF_STAGE=1`). The control uses page-cache fill without host staging (`STRATA_IO_PF_STAGE=0`). CPU prefill sharing and separate pinned expert staging were disabled. The exact prompt SHA-256 is `705dea47aafbfc991d0616621f3a13bf0136a43c546d60c7693c2efdced4d3a3`. The Q2_0 model revision and pack/profile identities are in the [local artifact record](../2026-10-11-phase3-q2-admission/artifact-identities.json); model files stayed in `~/models/`.

A harness guard exposed a boundary case before the measured pair: it reserved exactly `prompt + output` context, which Strata rejects. `context_reservation()` now leaves 32 extra tokens while retaining the 8,192 minimum. The 32K/8 cell therefore used context 32,808. Its regression tests pass. The native Q2 PLE pack has no `experts.bin`; for whole-device block telemetry the harness was given the actual first Q2_0 GGUF shard explicitly. The campaign ran in a systemd scope with `MemoryMax=24G`, memory and I/O accounting, plus the six-GiB supervisor.

Three complete randomized pairs are available: one standalone pilot and two pairs from a later three-pair campaign. They share the same day, binary (`sha256: bdde041e60d8593dac593a846d471c117fee2c5397b01dfd99c9502253dd0f7d`), prompt, cache, context, transfer modes, and 24-GiB cap. Pair order was fill/stage, fill/stage, and stage/fill. All pairs emitted the same eight IDs within each pair, matched all nine recorded persistent-state fields, and selected exactly 3,000 cache slots in both arms.

The median paired request-time delta was +16.96% (stage slower); a paired bootstrap 95% percentile interval was −0.50% to +33.43%. The interval is broad with three pairs and includes zero. Prompt-time deltas followed the same inconsistent pattern (median +17.17%, interval −0.52% to +33.81%); decode changes were small. Scoped read deltas also changed sign, with a median reduction of 1.234 decimal GB for staging. Page-fault counts varied widely. This does not establish an end-to-end benefit or a stable cost, and neither mode is promoted.

The initial one-pair campaign passed with 17.15 GiB minimum host availability and 10.13 GiB minimum effective cgroup headroom. The later campaign completed its first two pairs, then the supervisor stopped the next engine startup at 5.908 GiB effective headroom; host availability remained 17.25 GiB and OOM events were zero. That third startup submitted no request and is retained as a pressure abort. It does not invalidate the four earlier arms, but illustrates that cgroup file-cache charging can reach the guard while host availability remains high.

Read accounting uses per-request `io.stat` deltas from the scoped cgroup; whole-device block counters also exist but include unrelated activity. CPU clock observations across the campaigns ranged from 729.6 to 2,201.6 MHz; GPU observations ranged from 306 to 1,300.5 MHz; EMC readback stayed at 3,199 MHz. Clocks were dynamic and not controlled. Tegrastats provided no GPU clock samples during request windows in the per-arm sampler; named rail-energy estimates are board-wide, include unrelated activity, and are not additive or process-attributed. They do not support an energy-per-token claim.
